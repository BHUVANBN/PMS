PMS Project — Complete Analysis Report
Production Readiness Assessment
Executive Summary
The PMS (Project Management System) is a full-stack application with a Node.js/Express backend and a React/Vite frontend. It is not production-ready in its current state. The project has strong foundational architecture but contains critical security vulnerabilities, significant unimplemented features, dual authentication systems causing conflicts, leaked production secrets, and 44 ESLint errors. Below is a comprehensive breakdown.

🔴 CRITICAL ISSUES (Must Fix Before Production)
1. Secrets Exposed in .env — Committed to Repository
File: backend/.env

The .env file contains real production credentials and is not gitignored properly (the .gitignore only has 1 line: node_modules). This means actual secrets are potentially in git history.

MONGODB=mongodb+srv://bhuvanbn01_db_user:JxtgUj7f3vVZm89c@cluster0... ← Real DB credentials
CLOUDINARY_API_KEY=559884528695174
CLOUDINARY_API_SECRET=cE0GctefB1j0MpmqHKqie5eOlHQ
SMTP_PASS=ucuwyuudekloxmie  ← Real Gmail app password
JWT_SECRET=your_jwt_secret_key_here  ← Weak/placeholder secret
Fixes Required:

Add .env to .gitignore immediately
Rotate ALL exposed credentials (DB, Cloudinary, SMTP, JWT)
Use a strong randomly generated JWT_SECRET (min 256-bit)
Create a .env.example with placeholder values
2. Dual Authentication Systems — Conflict & Dead Code
Files: src/store/auth.js vs src/stores/authStore.js vs src/contexts/AuthContext.jsx

There are three separate auth implementations in the frontend:

src/store/auth.js — Mock store with hardcoded mock-jwt-token still present
src/stores/authStore.js — Zustand-based real auth store (not wired into the app)
src/contexts/AuthContext.jsx — The actual auth context used by the app
The mock store (src/store/auth.js) can allow bypassing authentication entirely in development if accidentally imported.

js
// src/store/auth.js — THIS IS STILL IN THE CODEBASE
login: async ({ username, password }) => {
  const fakeToken = 'mock-jwt-token'  // ← DANGEROUS
  ...
}
Fix: Remove src/store/auth.js and src/stores/authStore.js entirely. Consolidate auth into AuthContext.jsx.

3. No Rate Limiting on Authentication Endpoints
File: backend/index.js, backend/routes/auth.route.js

The roleBasedRateLimit middleware in roleAuth.js only sets req.rateLimit but never actually enforces it — it doesn't use express-rate-limit or any actual throttling. The login endpoint has zero brute-force protection.

js
// roleAuth.js:459 — This does NOTHING to actually limit requests
export const roleBasedRateLimit = (req, res, next) => {
  req.rateLimit = rateLimits[userRole] || 50;  // ← sets a property, enforces nothing
  next();
};
Fix: Install and configure express-rate-limit on /api/auth/* routes.

4. JWT Cookie Missing secure Flag
File: backend/controllers/auth.controller.js:55, backend/controllers/auth.controller.js:96

Cookies are set without secure: true, meaning they'll transmit over HTTP in production.

js
// auth.controller.js:55
res.cookie('token', token, { httpOnly: true, sameSite: 'lax', maxAge: 24*60*60*1000 });
// Missing: secure: true
Fix: Set secure: process.env.NODE_ENV === 'production' on all cookie settings.

5. Global console.log Statements With Sensitive Data in Production Code
File: backend/controllers/manager.controller.js:21-38

js
console.log(`Manager getMyProjects called by user: ${req.user.email} (ID: ${managerId})`);
console.log(`Found ${projects.length} projects for manager ${req.user.email}`);
// Also dumps ALL project names and manager IDs of every project in the DB
const allProjects = await Project.find({}).select('name projectManager');
console.log(`Total projects in database: ${allProjects.length}`);
allProjects.forEach(project => {
  console.log(`- ${project.name} managed by: ${project.projectManager}`);
});
This logs PII (email addresses) and makes an extra unfiltered database query on every project list call — a performance and security issue.

Fix: Remove all console.log debug statements. Use a proper logger (e.g., pWinston or pino) with log levels.

6. DB Connection After Server Start — Race Condition
File: backend/index.js:174-177

js
app.listen(PORT, async () => {
    await connectDB();  // ← DB connects AFTER server is already accepting requests
    console.log(`Server running on port ${PORT}`);
});
Requests arriving between listen() and connectDB() resolution will fail or crash.

Fix:

js
await connectDB();
app.listen(PORT, () => console.log(`Server running on port ${PORT}`));
7. SSE Endpoint Has No Authentication
File: backend/utils/realtime.js:59

js
app.get('/api/events', (req, res) => {
  const userId = req.query.userId;  // ← userId comes from query param, NO auth check
  // Anyone can subscribe to any user's channel by guessing their userId
Any unauthenticated user can subscribe to real-time events for any user.

Fix: Apply verifyToken middleware to the /api/events endpoint and derive userId from req.user._id.

8. Input Validation / Mass Assignment Vulnerability
File: backend/controllers/manager.controller.js:255

js
// updateProject — passes req.body DIRECTLY to MongoDB
const project = await Project.findOneAndUpdate(
  { _id: id, projectManager: managerId },
  req.body,  // ← Never sanitized or validated
  { new: true, runValidators: true }
);
Similarly in addModule:

js
project.modules.push(req.body);  // ← Raw body pushed to DB
An attacker can inject malicious fields (projectManager, __v, $where).

Fix: Whitelist allowed fields explicitly before DB operations.

12. Token Stored in Both Cookie and localStorage — Security Split
Files: frontend/src/contexts/AuthContext.jsx, frontend/src/services/api.js

The token is:

Set as an httpOnly cookie by the backend ✓
Also stored in localStorage by apiUtils.setAuthToken() ✗
localStorage tokens are accessible by JavaScript and vulnerable to XSS. The dual storage creates inconsistency about which token is actually used.

13. Inconsistent Response Format Across Controllers
Different controllers return inconsistent response shapes, making frontend parsing unreliable:

// hr.controller.js returns:

// No `success` key, uses `employees` not `data`
// auth.controller.js returns:
{ message: '...', token: '...', role: '...' }
// No `success`, no `data` wrapper
14. No Helmet.js for Security Headers
File: backend/index.js:91-96

Only 3 security headers are manually set. Missing critical headers:

Content-Security-Policy
Strict-Transport-Security (HSTS)
Referrer-Policy
Permissions-Policy
X-DNS-Prefetch-Control
Fix: Install and configure helmet package.

15. Missing MongoDB ObjectId Validation in Most Controllers
Most controllers in manager.controller.js and project.controller.js don't validate IDs before querying:

js
// No ObjectId validation:
const project = await Project.findOne({ _id: id, ... });
// If `id` is an invalid string like "abc", this throws a CastError
Only hr.controller.js properly uses mongoose.Types.ObjectId.isValid(id).

24. Missing Password Strength Validation
File: backend/controllers/auth.controller.js:80-101 (register), hr.controller.js:12-138 (createEmployee)

No minimum length, complexity, or strength requirements are enforced on passwords. A user can register with password "a".

25. No Pagination on List Endpoints
Multiple endpoints that could return large datasets have no pagination:

GET /api/admin/users — returns ALL users
GET /api/hr/employees — returns ALL employees
GET /api/manager/tickets — extracts ALL tickets from ALL projects in memory
This will cause performance issues at scale.

26. Sensitive Error Details Leaked to Client
File: backend/index.js:161, multiple controllers

js

  message: err.message || 'Internal Server Error'  // ← raw error messages to client
});
// hr.controller.js:134

In production, internal error messages (file paths, DB errors, etc.) should never reach the client.

27. LEAVE_STATUS and LEAVE_TYPES Naming Conflict in Models Index
File: backend/models/index.js:87-88

Two different schemas define the same enum names with potentially different values — a source of silent bugs.

28. No HTTPS Enforcement or HSTS
The backend has no middleware to redirect HTTP to HTTPS or set HSTS headers. Running in production without HTTPS means cookies (even httpOnly) are transmitted in plaintext.

29. socket.io-client Installed But SSE Used Instead
Frontend package.json: socket.io-client is a dependency, and socket.io is a backend dependency. However, the actual real-time implementation uses Server-Sent Events (SSE via realtime.js), not WebSockets. The socket.io dependencies appear to be unused dead weight.

30. tailwindcss and @tailwindcss/vite Mixed Versions

Tailwind v4 uses a completely different config format than v3. Having both installed is a conflict.
